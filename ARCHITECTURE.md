# Architecture Specification

## KISS Agent-First Fullstack Starter

**Status:** Architecture decisions approved
**Target:** Cursor IDE / AI Coding Agents
**Existing repository:** `danilger/ddd_strong_contract_agent_loop_starter`

---

# 1. Цель проекта

Переработать существующий стартер в минималистичную, надёжную и масштабируемую основу для разработки fullstack-приложений с использованием AI coding agents.

Стартер должен подходить как для небольших CRUD-приложений, так и для сложных SaaS-продуктов.

Основной сценарий разработки:

* Человек определяет требования, архитектуру и принимает ключевые решения.
* AI-агенты реализуют большую часть кода.
* Используются относительно недорогие coding-модели уровня DeepSeek Flash или Cursor Composer.
* Качество обеспечивается простотой архитектуры, строгими контрактами и автоматическими проверками.
* Человек должен иметь возможность быстро понимать и ревьюить результат.

## 1.1. Главный принцип

**KISS + минимальная достаточность.**

Каждая абстракция, зависимость, архитектурный слой и дополнительный инструмент должны иметь конкретное обоснование.

Запрещается добавлять архитектурные элементы исключительно ради соответствия шаблонам Clean Architecture, DDD, SOLID или другим методологиям.

Архитектура должна решать реальные задачи, а не демонстрировать знание паттернов проектирования.

## 1.2. Приоритеты

В порядке важности:

1. Простота понимания и ревью кода.
2. Надёжность агентской разработки.
3. Строгая типизация и runtime-валидация API.
4. Минимальное количество файлов и абстракций.
5. Локализация изменений внутри функциональных модулей.
6. Автоматическая проверка архитектурных ограничений.
7. Возможность постепенного усложнения архитектуры.
8. Производительность.

Производительность не должна достигаться ценой существенного усложнения без измеримой необходимости.

### Bun

Bun используется как:

* Runtime.
* Package manager.
* Test runner.
* Средство запуска TypeScript.

При этом приложение не должно без необходимости зависеть от специфичных Bun API.

Бизнес-логика должна оставаться максимально переносимой на Node.js.

Hono используется как HTTP-абстракция, а не прямой роутинг через `Bun.serve`.

Для проверки типов используется TypeScript compiler (`tsc --noEmit`).

Bun не заменяет полноценный TypeScript typecheck.

# 4. Backend Architecture

## 4.1. Modular Monolith

Backend организуется по функциональным модулям.

Пример:

```text
modules/
├── auth/
├── users/
├── billing/
└── subscriptions/
```

Каждый модуль содержит код, непосредственно относящийся к его функциональности.

Не использовать обязательную горизонтальную структуру:

```text
application/
domain/
infrastructure/
presentation/
```

Не создавать архитектурные слои заранее.

## 4.2. Progressive Architecture

Сложность структуры должна соответствовать сложности функциональности.

### Уровень 1. Простой CRUD

Минимум — контракт модуля + routes:

```text
users/
├── contract/
│   ├── schema.ts
│   └── endpoints.ts
└── users.routes.ts
```

HTTP-обработчик может напрямую выполнять простые операции с БД, если бизнес-логика отсутствует.

Импортировать напрямую из `contract/schema` и `contract/endpoints`. Не создавать `contract/index.ts`.

### Уровень 2. Бизнес-логика

```text
users/
├── contract/
│   ├── schema.ts
│   └── endpoints.ts
├── users.routes.ts
└── users.service.ts
```

Разделение ответственности:

**Contract (`contract/`):**

* Zod-схемы request/response (`schema.ts`).
* Явные endpoint-контракты: `input` + `responses` (`endpoints.ts`).
* Пишется и ревьюится до реализации handler’ов.
* Без barrel `index.ts` — прямые импорты.

**Routes:**

* HTTP.
* `implement(contract, handler)`.
* Вызов бизнес-функций.

**Service:**

* Бизнес-операции.
* Проверка бизнес-правил.
* Транзакции.
* Взаимодействие с БД и другими модулями.

### Уровень 3. Сложная предметная область

```text
billing/
├── contract/
│   ├── schema.ts
│   └── endpoints.ts
├── billing.routes.ts
├── billing.service.ts
├── billing.table.ts
├── billing.repository.ts
│
└── domain/
    ├── calculate-price.ts
    └── billing-policy.ts
```

Дополнительные файлы создаются только при появлении соответствующей сложности.

Не требуется автоматически создавать `repository.ts` или `domain/` для каждого модуля.

## 4.3. Функции вместо классов

Предпочитать обычные функции.

Не создавать классы только ради группировки методов.

Не использовать DI-контейнер.

Зависимости могут передаваться явно, когда это необходимо для тестирования или конфигурации.

Пример:

```typescript
export async function createUser(input: CreateUserInput) {
  // Business logic
}
```

Вместо:

```typescript
@Injectable()
export class CreateUserCommandHandler {
  // ...
}
```

Классы допустимы, если у объекта действительно есть состояние, жизненный цикл или другое конкретное обоснование.

## 4.4. Repository Pattern

Repository Pattern не используется по умолчанию.

Сервисам разрешено напрямую работать с Drizzle.

```typescript
export async function getUser(id: string) {
  return db.query.users.findFirst({
    where: eq(users.id, id),
  });
}
```

Отдельный repository допускается, если:

* Запросы стали достаточно сложными.
* Повторяется существенная логика доступа к данным.
* Необходимо изолировать сложную инфраструктурную интеграцию.
* Есть конкретная потребность в альтернативной реализации.

Не создавать интерфейсы репозиториев автоматически.

## 4.5. CQRS

Не использовать `@nestjs/cqrs`, CommandBus и QueryBus.

Разделять чтение и запись обычными функциями, если это улучшает читаемость.

Не создавать отдельные классы команд и запросов.

Event sourcing, sagas, outbox и аналогичные механизмы добавляются только при наличии соответствующих требований.

# 5. Границы модулей

Изоляция модулей обеспечивается линтером.

Не использовать для этой задачи DI-контейнер, обязательные repository ports или сложную систему адаптеров.

## 5.1. Основные правила

1. Модули не должны обращаться к внутренней реализации других модулей.
2. Межмодульное взаимодействие осуществляется через явно экспортированные публичные функции.
3. Прямой доступ к таблицам другого модуля запрещён по умолчанию.
4. Циклические зависимости запрещены.
5. Модуль не должен зависеть от HTTP-обработчиков другого модуля.
6. Общие утилиты не должны зависеть от бизнес-модулей.

## 5.2. Публичный API модуля

Публичный API может быть организован через `index.ts`.

Однако `index.ts` не требуется для внутренних директорий и каждого файла.

Пример:

```text
users/
├── index.ts
├── users.routes.ts
├── users.service.ts
└── users.table.ts
```

`index.ts` экспортирует только те функции, которые разрешено использовать другим модулям.

Внутри модуля допускаются прямые относительные импорты.

## 5.3. Architecture Linting

Настроить автоматические проверки:

* Запрет приватных межмодульных импортов.
* Запрет циклических зависимостей.
* Запрет импортов server-кода в client.
* Запрет зависимости shared-кода от бизнес-модулей.
* Контроль направления зависимостей frontend.

Предпочитать готовые правила ESLint/Oxlint.

Не писать собственный линтер, если существующие инструменты позволяют реализовать необходимые ограничения.

Не создавать сложную систему архитектурных проверок ради формального соблюдения паттернов.

# 6. API Contracts

**Это обязательная часть архитектуры.**

Отдельный workspace `contract/` удаляется.

При этом строгие API-контракты сохраняются.

## 6.1. Требования

Каждый API endpoint должен иметь:

1. Статически типизированный request.
2. Статически типизированный response.
3. Runtime-валидацию request.
4. Runtime-валидацию response.
5. Явное описание допустимых HTTP-статусов.
6. Типизированное представление ожидаемых ошибок.

Контракт должен проверять не только успешные ответы, но и предусмотренные JSON-ответы с ошибками.

## 6.2. Предпочтительное решение

Исследовать использование:

* Hono.
* `@hono/zod-openapi`.
* Zod.
* Типизированного клиента Hono.

`@hono/zod-openapi` является предпочтительным кандидатом, но не окончательно утверждённой реализацией.

**Критически важно:** декларация response schema не гарантирует runtime-валидацию ответа.

Необходимо убедиться, что выбранная реализация действительно проверяет возвращаемые данные.

## 6.3. Runtime Response Validation

Требования:

* Проверка фактического JSON перед отправкой.
* Выбор схемы по HTTP-статусу и типу содержимого.
* Ошибка при несоответствии ответа контракту.
* Отсутствие утечки некорректного ответа клиенту.
* Проверка должна быть обязательной, а не зависеть от того, вспомнил ли агент вызвать `.parse()`.

Предпочтительно использовать существующий механизм библиотеки.

Если готового решения нет, допускается небольшой централизованный механизм проверки ответов.

Но запрещается создавать собственный универсальный API-фреймворк поверх Hono.

Нужно отдельно учитывать ответы без тела, streaming, файлы и другие форматы, для которых обычная JSON-валидация неприменима.

## 6.4. Размещение контрактов

Контракты модуля всегда живут в `modules/<name>/contract/`:

```text
modules/
└── users/
    ├── contract/
    │   ├── schema.ts      # Zod-схемы тел и сущностей
    │   └── endpoints.ts   # RouteContract: input + responses
    ├── users.routes.ts
    └── users.service.ts
```

Импорты: `./contract/schema`, `./contract/endpoints`. Не добавлять `contract/index.ts`.

Не создавать корневой `src/contracts/` без реальной необходимости централизовать контракты между модулями.

Правило: сначала `contract/`, затем реализация в `*.routes.ts` / `*.service.ts`.

## 6.5. Frontend API Client

Frontend должен использовать типизированный API-клиент.

Не дублировать вручную request/response TypeScript-типы.

Не создавать отдельные frontend DTO, если они полностью повторяют серверный контракт.

Клиент не должен импортировать серверную бизнес-логику, БД или runtime-зависимости.

Допускаются только type-only зависимости от серверного API и общие схемы, безопасные для браузера.

Проверить совместимость выбранного контрактного решения с Hono RPC и клиентским выводом типов.

Если выбранная библиотека не обеспечивает полноценную типизацию клиента, исследовать существующие OpenAPI-based решения.

Не писать собственный генератор клиента.

# 7. Database

Использовать Drizzle ORM.

## 7.1. SQLite и PostgreSQL

SQLite подходит для небольших приложений и простого развёртывания.

PostgreSQL используется при наличии требований к конкурентной записи, масштабированию, эксплуатации или специфичным возможностям СУБД.

Не добавлять обе СУБД одновременно в стартовый проект без необходимости.

Не создавать универсальный слой абстракции для переключения между SQLite и PostgreSQL.

## 7.2. Схемы таблиц

Таблицы могут располагаться внутри функциональных модулей:

```text
modules/
├── users/
│   └── users.table.ts
│
└── billing/
    └── billing.table.ts
```

`db/schema.ts` используется для централизованного экспорта схем.

Миграции хранятся в `db/migrations/`.

## 7.3. Транзакции

Использовать транзакции Drizzle напрямую.

Не создавать собственный Unit of Work.

Не создавать транзакционные интерфейсы без конкретной необходимости.

# 8. Frontend Architecture

Использовать упрощённую Feature-Sliced Design.

Базовая структура:

```text
client/
├── app/
├── pages/
├── features/
└── shared/
```

Не создавать все стандартные слои FSD автоматически.

`entities/` и `widgets/` добавляются при реальной необходимости.

## 8.1. Основные правила

* Организация преимущественно по функциональности.
* Компоненты должны иметь понятную ответственность.
* Большие JSX-компоненты необходимо декомпозировать.
* Не смешивать сложную бизнес-логику с представлением.
* Избегать циклических зависимостей.
* Не создавать бессмысленные компоненты-обёртки.
* Не использовать Atomic Design.

Файл размером более 400 строк является сигналом для проверки необходимости декомпозиции, но не автоматическим основанием для разделения.

## 8.2. FSD Linting

Использовать автоматическую проверку направления импортов.

Не требовать создания `index.ts` в каждой директории.

Не создавать сегменты `ui/model/api/lib` исключительно ради соответствия FSD.

# 9. Agent-First Development

Архитектура должна учитывать ограниченные возможности относительно небольших coding-моделей.

## 9.1. Минимизация контекста

Предпочитать решения, при которых реализация одной функциональности требует изменений в небольшом количестве связанных файлов.

Не распределять одну простую операцию по множеству классов и архитектурных слоёв.

## 9.2. Explicit Dependencies

Предпочитать:

* Прямые импорты.
* Обычные функции.
* Явные параметры.
* Понятные вызовы.

Избегать:

* Скрытой регистрации обработчиков.
* Необязательной рефлексии.
* Динамического поиска зависимостей.
* Избыточных фабрик.
* Service locator.
* DI-контейнеров.

## 9.3. Ограничение абстракций

Перед созданием новой абстракции агент должен определить:

1. Какую конкретную проблему она решает?
2. Почему существующего кода недостаточно?
3. Можно ли решить задачу проще?
4. Уменьшит ли она общую сложность системы?

Если обоснования нет, абстракцию не создавать.

## 9.4. Правила изменения кода

Агент должен:

* Изменять минимально необходимое количество файлов.
* Не проводить несвязанный рефакторинг.
* Не создавать универсальные решения для гипотетических требований.
* Не добавлять зависимости без обоснования.
* Не изменять публичные контракты без необходимости.
* Добавлять тесты на существенную бизнес-логику.
* Проверять результат автоматическими инструментами.

# 10. OpenSpec и SDLC

       ↓
Deterministic Checks

* Дублирующихся OpenSpec-конфигураций.

# 11. Quality Gates

Автоматические проверки обязательны.

Минимальный набор:

```text
typecheck
lint
test
build
```

E2E-тестирование используется для критических пользовательских сценариев.

## 11.1. Typecheck

Проверка TypeScript без ошибок.

## 11.2. Lint

Проверка:

* Качества кода.
* Архитектурных границ.
* Запрещённых импортов.
* Циклических зависимостей.

## 11.3. Tests

Тестировать:

* Бизнес-правила.
* API-контракты.
* Критические операции.
* Обработку ошибок.
* Взаимодействие с БД при необходимости.

Не создавать тесты исключительно ради покрытия каждой тривиальной функции.

## 11.4. Contract Tests

Обязательно проверить:

* Невалидный request отклоняется.
* Валидный request принимается.
* Невалидный response обнаруживается.
* Некорректный response не отправляется как успешный ответ.
* HTTP-статусы соответствуют контракту.
* Предусмотренные ошибки соответствуют своим схемам.

Особенно важно иметь тест, который намеренно возвращает ответ неправильной структуры.

Он должен завершаться ошибкой независимо от того, какой агент реализовал endpoint.

## 11.5. LLM Review

LLM-review не заменяет детерминированные проверки.

Дополнительные LLM-проверки допускаются после успешного прохождения typecheck, lint и tests.

Не делать дорогостоящие multi-model evaluations обязательными для каждого изменения.

# 12. Что не входит в базовую архитектуру

По умолчанию не использовать:

* NestJS.
* `@nestjs/cqrs`.
* CommandBus / QueryBus.
* Обязательный CQRS.
* DI-контейнер.
* Repository interfaces.
* Unit of Work abstraction.
* Обязательные Domain Entities.

* Domain Events для обычного CRUD.
* Event Sourcing.
* Saga.
* Outbox.
* Microservices.

Любой из этих механизмов может быть добавлен при появлении реальной необходимости.

Запрет относится к использованию **по умолчанию**, а не к технологии как таковой.

# 14. Критерии готовности

Новый стартер считается готовым, когда:

1. Backend работает на Bun + Hono.
2. Frontend работает на React + Vite.
3. Используется единая структура проекта.
4. NestJS и обязательный CQRS удалены.
5. Нет DI-контейнера.
6. Нет обязательных repository interfaces.
7. Auth работает и покрыт необходимыми тестами.
8. Request проходит runtime-валидацию.
9. Response проходит runtime-валидацию.
10. Контракты доступны типизированному frontend-клиенту.
11. Архитектурные ограничения проверяются линтером.
12. Есть единый OpenSpec.
13. Нет обязательного LangGraph loop.
14. Проходят typecheck, lint, tests и build.
15. Приложение можно запустить минимальным количеством команд.
16. Добавление простой CRUD-функциональности не требует создания множества инфраструктурных файлов.

# 15. Основные архитектурные принципы

**KISS:** простота важнее архитектурной красоты.

**YAGNI:** не реализовывать гипотетические требования.

**Modular Monolith:** функциональная модульность без микросервисной инфраструктуры.

**Vertical Slices:** связанный код располагается рядом.

**Progressive Architecture:** архитектура усложняется только по мере необходимости.

**Explicit Dependencies:** обычные импорты и функции вместо скрытой магии.

**Strict Contracts:** runtime-валидация request и response.

**Deterministic Quality Gates:** качество проверяется инструментами, а не только LLM.

**Agent-Friendly Code:** минимальное количество файлов, понятные зависимости, локальные изменения.

# 16. Инструкция для Cursor

Используй этот документ как целевую архитектурную спецификацию.

Твоя задача: помочь переработать существующий стартер, а не создать новый сложный архитектурный фреймворк.

**На первом шаге не изменяй код.**

Сначала:

1. Проанализируй существующий репозиторий.
2. Сопоставь его с целевой архитектурой.
3. Выдели компоненты, которые нужно удалить.
4. Выдели компоненты, которые нужно сохранить.
5. Исследуй библиотеки для строгих API-контрактов.
6. Проверь возможность автоматической runtime-валидации response.
7. Предложи минимальную конфигурацию линтера для изоляции модулей.
8. Подготовь поэтапный план миграции.

При наличии нескольких решений выбирай то, которое обеспечивает необходимые гарантии с наименьшей общей сложностью.

Не добавляй новые архитектурные слои без согласования.

Не ослабляй требования к API-контрактам ради уменьшения количества кода.

**Ключевая цель: не минимальное количество строк любой ценой, а минимальная сложность при сохранении надёжности.**
